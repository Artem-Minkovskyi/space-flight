# Лабораторна №7 — протокол вимірювання продуктивності

> У цьому документі немає вигаданих вимірювань. Заповніть таблиці після запуску гри на цільовому комп'ютері та збережіть скриншоти Chrome DevTools у `docs/performance/screenshots/`.

## Відтворюваний сценарій

1. `npm install`.
2. У першому терміналі: `npm run dev:server`.
3. Для 8 клієнтів-ботів протягом 30 секунд: `LOAD_DURATION_MS=30000 npm run test:load -- 8`.
4. Для запису саме браузерного main thread відкрий гру у Chrome та відтвори 30-секундний сценарій з 8 гравцями; збережи Performance trace.
5. DevTools → Performance → Record. Увімкнути Screenshots та Memory; зупинити запис після 30 секунд.
6. Зберегти flame chart та Memory/GC скриншоти в `docs/performance/screenshots/`.
7. Повторити після оптимізацій з тим самим сценарієм.

## Зміни в коді

- `Explosion` повторно використовує об'єкти частинок через `ObjectPool`; під час оновлення позиція змінюється покомпонентно, без створення нового `Vector2` кожен кадр.
- Вузька фаза зіткнень використовує `SpatialHash`: сутності індексуються за AABB, а точна перевірка кола залишається у `checkCircleCollision`.
- Обов'язково порівняти результат до/після на однаковій кількості об'єктів; якщо кількість об'єктів мала, побудова хешу може коштувати дорожче за простий подвійний цикл.

## Web Worker — висновок

Симуляція корабля й зіткнення працюють зі спільними змінюваними об'єктами `World`, Entity та `Vector2`. Перенесення цього коду у Worker потребувало б серіалізації стану кожного кадру й синхронізації результату назад на main thread. У поточному проєкті немає окремого CPU-важкого незалежного компонента ботів, який можна безпечно винести без зміни архітектури. Тому Worker не додавався до production loop: спочатку усуваються алокації й broad-phase O(n²), а рішення про Worker приймається лише після профілювання. Це свідоме архітектурне рішення, а не твердження про виміряне прискорення.

## Навантаження сервера

Запуск: `npm run dev:server`, потім в іншому терміналі `npm run test:load`.

Скрипт окремо під'єднує 8, 32, 64 і 128 WebSocket-клієнтів, відправляє input-пакети та рахує p50/p95/p99 інтервалів snapshot. Інтервал snapshot — непрямий показник, а не точний час server tick. Значення p99 понад 33 ms позначається попередженням. Для точного server tick duration додайте вимірювання `performance.now()` навколо серверного `setInterval` і збережіть гістограму.
