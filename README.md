Браузерна гра **Space Flight**, розроблена на Vanilla JavaScript, HTML5 Canvas 2D та Vite у межах лабораторних робіт №1–4 з дисципліни «JavaScript».

# Опис проєкту

Space Flight — це двовимірна браузерна космічна гра, у якій користувач керує космічним кораблем, знищує астероїди, збирає бонуси та взаємодіє з ігровим середовищем.

Основні можливості:

- керування кораблем за допомогою клавіатури;

- прискорення, гальмування та поворот;

- переміщення об'єктів через межі арени;

- стрільба та система зіткнень;

- здоров'я корабля та астероїдів;

- вибухи й анімація частинок;

- бонуси для відновлення здоров'я;

- система рахунку;

- звукові ефекти;

- завантаження ігрових ресурсів із відображенням прогресу;

- Lobby для введення імені та вибору кімнати;

- різні налаштування складності гри.

# Лабораторна робота №1 — The Event Loop Is the Game Loop

## Мета роботи

Дослідити принципи роботи Event Loop у JavaScript та реалізувати ігровий цикл із фіксованим кроком симуляції, обробкою клавіатури, Canvas 2D і вимірюванням продуктивності.

## Реалізовані можливості

### 1. Ігровий цикл

У модулі `src/loop.js` реалізовано функцію `createLoop()`, яка організовує роботу симуляції та рендерингу.

Використовується `requestAnimationFrame()` і патерн Accumulator.

Фізична симуляція виконується з фіксованим кроком:

```js
const step = 1 / 60;
```

Таким чином, логіка гри не залежить безпосередньо від частоти оновлення монітора.

### 2. Обробка клавіатури

У `src/input.js` реалізовано функцію `createInput()`, яка використовує замикання (Closure) для зберігання стану натиснутих клавіш.

Користувач може керувати кораблем:

- `W` або `↑` — прискорення;

- `S` або `↓` — гальмування;

- `A` або `←` — поворот ліворуч;

- `D` або `→` — поворот праворуч.

### 3. Фізична модель корабля

У модулі `src/sim/ship.js` реалізовано фізику руху корабля:

- прискорення;

- поворот;

- інерція;

- опір;

- обмеження максимальної швидкості.

Фізична логіка відокремлена від DOM і Canvas.

### 4. Canvas та інтерполяція

У `src/render/canvas.js` реалізовано налаштування Canvas з урахуванням `devicePixelRatio` та зміни розміру вікна.

У `src/render/draw.js` реалізовано відображення ігрового середовища.

Інтерполяція між попереднім і поточним станом корабля забезпечує плавність руху.

### 5. HUD та продуктивність

Інтерфейс відображає три показники:

- **Simulation** — кількість кроків симуляції за секунду;

- **Render** — кількість кадрів за секунду;

- **Frame Time** — час кадру в мілісекундах.

## Експерименти

### Експеримент 1. Блокування головного потоку

У функцію `render()` тимчасово додавалося штучне блокування головного потоку на 100 мс кожні 5 секунд.

Для цього використовувався синхронний цикл `while`.

Результат: під час блокування браузер не міг своєчасно виконувати JavaScript, оновлювати кадри та обробляти інші завдання. Спостерігалося збільшення часу кадру та можливе зниження FPS.

Після експерименту блокування було видалено.

### Експеримент 2. requestAnimationFrame() та setInterval()

Порівнювалася робота `requestAnimationFrame()` і `setInterval()` з інтервалом 16 мс.

Результати вимірювань `setInterval()`:

| Вимірювання | Кількість інтервалів | Середнє відхилення | Максимальне відхилення |

| ----------- | -------------------: | -----------------: | ---------------------: |

| 1 | 623 | 0,57 мс | 3,90 мс |

| 2 | 562 | 2,39 мс | 776,10 мс |

На додаткових вимірюваннях зафіксовано відхилення приблизно до 984,9 мс. Частина вимірювань виконувалася під час або поруч зі штучним блокуванням головного потоку.

Висновок: `setInterval()` не гарантує точного інтервалу виконання. `requestAnimationFrame()` краще підходить для анімації, оскільки узгоджує рендеринг із циклом відображення браузера.

### Експеримент 3. Fixed Timestep та Variable Timestep

Порівнювалися два способи оновлення фізичної симуляції:

- **Variable Timestep** — симуляція виконується один раз за кадр із фактичним значенням `dt`.

- **Fixed Timestep** — симуляція виконується з постійним кроком 1/60 секунди за допомогою акумулятора часу.

Для кожного режиму проводилося п'ятисекундне вимірювання руху корабля.

Початкові координати в обох вимірюваннях:

- X = 453,50;

- Y = 284,13.

Отримані результати:

| Показник | Variable Timestep | Fixed Timestep |

| ---------------------- | ----------------: | -------------: |

| Кінцева координата X | 695,03 | 530,98 |

| Кінцева координата Y | 261,74 | 237,39 |

| Зміщення X | 241,53 | 77,48 |

| Зміщення Y | -22,38 | -46,74 |

| Відстань між позиціями | 242,57 | 90,49 |

Умови вимірювання не були повністю однаковими, тому ці значення не можна використовувати як точне кількісне порівняння швидкості двох режимів.

Висновок: Fixed Timestep забезпечує сталий крок фізичної симуляції, незалежний від частоти рендерингу.

# Лабораторна робота №2 — Objects, Prototypes and this

## Мета роботи

Поглибити практичні навички роботи з об'єктами JavaScript, класами, прототипами, наслідуванням, контекстом `this` та композицією поведінки.

## Реалізовані можливості

### 1. Клас Vector2

Створено клас `Vector2` для виконання двовимірних векторних обчислень.

Основні операції:

- `add()` — додавання;

- `sub()` — віднімання;

- `scale()` — множення на число;

- `length()` — обчислення довжини;

- `normalize()` — нормалізація;

- `rotate()` — обертання;

- `dot()` — скалярний добуток.

Методи, які виконують математичні операції, повертають нові екземпляри `Vector2`, не змінюючи початковий вектор.

### 2. Базовий клас Entity

Створено базовий клас `Entity`, який містить спільні властивості ігрових об'єктів:

- `id` — унікальний ідентифікатор;

- `position` — позиція;

- `velocity` — швидкість;

- `radius` — радіус;

- `kind` — тип сутності;

- `dead` — стан знищення.

Для генерації ідентифікаторів використовується приватне статичне поле `#nextId`.

Метод `update(deltaTime)` оновлює стан сутності, а `destroy()` позначає її для видалення.

### 3. Наслідування

На основі `Entity` створено спеціалізовані класи:

```text

Entity

├── Ship

├── Bullet

├── Asteroid

├── Pickup

└── Explosion

```

Особливості класів:

**Ship**

- керування кораблем;

- кут повороту;

- здоров'я;

- методи `takeDamage()` та `heal()`;

- приватне поле `#hp`.

**Bullet**

- шкода;

- час життя `ttl`;

- рух у напрямку пострілу.

**Asteroid**

- здоров'я;

- рух;

- можливість знищення.

**Pickup**

- бонус для корабля;

- відновлення здоров'я.

**Explosion**

- частинки;

- тривалість анімації;

- поступове зникнення.

Використовується один рівень наслідування, що дозволяє уникнути надмірно складної ієрархії класів.

### 4. Клас World

Для керування ігровими сутностями реалізовано клас `World`.

Він використовує `Map`, де ключем виступає ідентифікатор сутності, а значенням — її екземпляр.

Основні можливості:

- `spawn()` — додавання сутності;

- `despawn()` — позначення сутності для видалення;

- `sweep()` — видалення знищених сутностей;

- `[Symbol.iterator]` — ітерація по сутностях;

- `ofKind()` — генератор для отримання сутностей певного типу.

Фізичне видалення відокремлено від логічного знищення. Це дозволяє безпечно змінювати колекцію під час симуляції.

### 5. Зіткнення та бойова система

Реалізовано систему зіткнень між ігровими об'єктами.

Під час зіткнення можуть відбуватися:

- пошкодження корабля;

- пошкодження астероїдів;

- знищення куль;

- зменшення здоров'я;

- створення вибухів;

- нарахування очок.

Після знищення корабля передбачено його відродження.

### 6. Композиція поведінки

Для реалізації самонаведення астероїдів використано композиційний підхід.

Функція `attachHoming()` додає сутності поведінку самонаведення без створення додаткових класів і складного наслідування.

Також реалізовано систему підбирання бонусів.

### 7. Контекст this

Під час роботи досліджено особливості контексту `this` у JavaScript.

Значення `this` залежить від способу виклику функції, а не лише від місця її оголошення.

Для збереження необхідного контексту можуть використовуватися:

- `bind()`;

- `call()`;

- `apply()`;

- стрілкові функції;

- передавання контексту через замикання.

Це особливо важливо під час роботи з методами класів, callback-функціями та обробниками подій.

# Лабораторна робота №3 — Async JavaScript

## Мета роботи

Дослідити асинхронну модель JavaScript, роботу Promise, async/await, Fetch API, AbortController, EventTarget та Web Audio API.

У межах роботи реалізовано асинхронне завантаження ігрових ресурсів, систему прогресу, обробку помилок і Lobby для вибору кімнати.

## 1. Promise та async/await

Асинхронні операції використовуються для завантаження ресурсів, отримання JSON і декодування аудіо.

Основні стани Promise:

- `pending` — очікування результату;

- `fulfilled` — успішне виконання;

- `rejected` — помилка.

Приклад:

```js
async function loadData() {
  try {
    const response = await fetch('/api/rooms.json');

    if (!response.ok) {
      throw new Error(`HTTP error: ${response.status}`);
    }

    return await response.json();
  } catch (error) {
    console.error('Помилка завантаження:', error);

    throw error;
  }
}
```

`async/await` дозволяє записувати асинхронний код у послідовній формі, а `try/catch` — обробляти помилки.

## 2. Послідовне та паралельне завантаження

Послідовне завантаження:

```js
const image = await loadImage('/assets/ship.svg');

const audio = await loadAudio('/assets/shot.wav');

const config = await loadJson('/api/rooms.json');
```

У цьому випадку кожна операція починається після завершення попередньої.

Паралельне завантаження:

```js
const [image, audio, config] = await Promise.all([
  loadImage('/assets/ship.svg'),

  loadAudio('/assets/shot.wav'),

  loadJson('/api/rooms.json'),
]);
```

У цьому випадку операції запускаються незалежно одна від одної, тому загальний час очікування зазвичай менший.

Важлива відмінність: `Promise.all()` відхиляється, якщо одна з операцій завершується помилкою. `Promise.allSettled()` очікує завершення всіх операцій і повертає статус кожної.

У менеджері ресурсів проєкту результати завантаження збираються з можливістю відстежувати завершення окремих операцій.

## 3. Завантаження ресурсів

У директорії `src/assets/` реалізовано два основні модулі:

- `loader.js`;

- `assetManager.js`.

Файл `public/manifest.json` містить перелік ресурсів гри:

```json
{
  "images": {
    "ship": "/assets/sprites/ship.svg",

    "bullet": "/assets/sprites/bullet.svg",

    "asteroid": "/assets/sprites/asteroid.svg",

    "explosion": "/assets/sprites/explosion.svg"
  },

  "audio": {
    "shot": "/assets/audio/shot.wav",

    "hit": "/assets/audio/hit.wav",

    "explosion": "/assets/audio/explosion.wav"
  },

  "json": {
    "arena": "/api/rooms.json"
  }
}
```

Реалізовано функції:

- `loadImage()` — завантаження зображень;

- `loadAudio()` — завантаження та декодування аудіо;

- `loadJson()` — отримання JSON;

- `fetchJson()` — запит із перевіркою HTTP-відповіді;

- `withRetry()` — повторні спроби завантаження.

Для повторних спроб використовується експоненційна затримка з випадковим відхиленням (jitter).

Помилки HTTP 4xx не повторюються, оскільки зазвичай вони вказують на некоректний запит або відсутній ресурс.

## 4. Прогрес завантаження

Під час завантаження ресурсів користувач бачить:

- кількість завантажених файлів;

- загальну кількість файлів;

- відсоток виконання;

- назву поточного ресурсу.

Для відображення прогресу використовується HTML-індикатор із динамічною зміною ширини.

Гра не запускається до успішного завершення завантаження необхідних ресурсів.

Передбачено можливість скасування завантаження через `AbortController` та повторного запуску.

## 5. Web Audio API

Для відтворення звукових ефектів створено `src/audio.js`.

Реалізовано клас `AudioManager`, який:

- створює `AudioContext`;

- відновлює призупинений контекст;

- приймає декодовані аудіобуфери;

- відтворює звукові ефекти;

- дозволяє вимкнути звук;

- закриває аудіоконтекст під час завершення роботи.

`AudioContext` створюється після взаємодії користувача з кнопкою запуску, що враховує обмеження браузерів щодо автоматичного відтворення аудіо.

## 6. EventTarget та CustomEvent

Для зв'язку між ігровою симуляцією та аудіосистемою реалізовано `src/events.js`.

Створено клас `GameEvents`, який успадковується від `EventTarget`.

Він генерує події:

| Подія | Призначення |

| ---------- | ------------------------- |

| `fired` | Корабель здійснив постріл |

| `hit` | Відбулося зіткнення |

| `exploded` | Об'єкт знищено |

Для передачі додаткової інформації використовується `CustomEvent`.

Таким чином, симуляція не залежить безпосередньо від аудіосистеми.

## 7. Lobby — вибір гравця та кімнати

Реалізовано Lobby для підготовки до гри.

У Lobby користувач може:

1. Ввести ім'я гравця.

# Лабораторна робота №4 — Multiplayer Networking and Replay

## Мета роботи

Розширити гру Space Flight мережевою взаємодією між гравцями, реалізувати запис станів кораблів та подій ігрової сесії, а також створити механізм Replay для відтворення записаних переміщень.

## Реалізовані можливості

### 1. Серверна та клієнтська архітектура

Проєкт організовано як застосунок із клієнтською та серверною частинами. Клієнт відповідає за ігровий інтерфейс, симуляцію та відображення, а сервер — за мережеві підключення, кімнати й обмін даними між гравцями.

### 2. WebSocket та багатокористувацький режим

Для обміну даними між клієнтом і сервером використовується WebSocket.

Реалізовано:

- підключення гравця до сервера;

- створення та вибір ігрових кімнат;

- приєднання гравців до кімнат і вихід із них;

- оновлення списку учасників;

- обмін повідомленнями чату;

- передавання стану корабля іншим учасникам кімнати.

Стан корабля містить координати, швидкість, кут повороту, рівень здоров'я, стан прискорення та ознаку знищення. На клієнті віддалені кораблі відображаються з інтерполяцією між отриманими станами.

### 3. Запис подій матчу

Для збереження подій використовується формат NDJSON (Newline Delimited JSON). Кожен запис є окремим JSON-об'єктом у новому рядку.

Журнал зберігається у файлі:

```text

server/logs/matches.ndjson

```

До журналу записуються події, пов'язані з кімнатами, підключеннями гравців, чатом і станами кораблів.

Щоб обмежити обсяг журналу та навантаження на сервер, стани кораблів записуються з інтервалом приблизно 200 мілісекунд для кожного підключення.

### 4. Читання журналу та Replay API

Для читання NDJSON-журналу створено модуль `server/src/logs/replay.js`. Він обробляє файл потоково: читає дані, розбирає окремі рядки як JSON та передає події обробнику.

Для отримання записаних подій реалізовано HTTP-маршрут:

```http

GET /api/replay

```

Маршрут повертає JSON із кількістю знайдених подій та масивом подій. У разі помилки читання сервер повертає повідомлення про помилку.

### 5. Інтерфейс Replay

У клієнтському інтерфейсі додано панель Replay. Вона дозволяє:

- завантажити запис із сервера;

- запустити відтворення кнопкою PLAY;

- призупинити відтворення кнопкою PAUSE;

- переміщуватися записом за допомогою часової шкали;

- змінювати швидкість відтворення: 0.5x, 1x або 2x.

Під час завантаження клієнт відбирає події типу `player:state`, групує їх за гравцями та впорядковує за часовими мітками. Якщо доступний запис поточної кімнати, використовується він; інакше вибирається кімната з останніх записаних подій.

Для плавного руху між збереженими позиціями використовується інтерполяція координат і кута повороту корабля.

Replay відтворює записані стани кораблів гравців. Він поки не відновлює повну симуляцію всіх об'єктів гри: астероїдів, куль, зіткнень та інших подій фізичного світу. # Порядок виконання JavaScript: 5 прикладів

У JavaScript синхронний код виконується через Call Stack. Асинхронні callback-функції потрапляють до відповідних черг.

Основні поняття:

- **Call Stack** — стек викликів;

- **Task Queue** — черга задач;

- **Microtask Queue** — черга мікрозадач;

- **Event Loop** — механізм координації виконання;

- **requestAnimationFrame** — callback перед наступним малюванням браузера.

## Приклад 1. Синхронний код і Promise

```js
console.log('1');

Promise.resolve().then(() => {
  console.log('2');
});

console.log('3');
```

Результат:

```text

1

3

2

```

Пояснення:

1. Спочатку виконується синхронний код.

2. Callback Promise додається до черги Microtasks.

3. Після завершення синхронного коду виконується мікрозадача.

## Приклад 2. Promise та setTimeout

```js
console.log('A');

setTimeout(() => {
  console.log('B');
}, 0);

Promise.resolve().then(() => {
  console.log('C');
});

console.log('D');
```

Результат:

```text

A

D

C

B

```

Пояснення:

- `A` і `D` — синхронний код;

- `C` — мікрозадача;

- `B` — задача таймера.

Мікрозадачі виконуються перед переходом до наступної задачі.

## Приклад 3. setTimeout усередині Promise

```js
console.log('start');

Promise.resolve().then(() => {
  console.log('promise');

  setTimeout(() => {
    console.log('timer');
  }, 0);

  Promise.resolve().then(() => {
    console.log('nested promise');
  });
});

setTimeout(() => {
  console.log('second timer');
}, 0);

console.log('end');
```

Результат:

```text

start

end

promise

nested promise

second timer

timer

```

Пояснення:

1. `start` і `end` виконуються синхронно.

2. Виконується перша мікрозадача `promise`.

3. Вона додає таймер `timer` та нову мікрозадачу.

4. Перед переходом до таймерів виконується `nested promise`.

5. Після цього виконуються задачі таймерів у порядку постановки в чергу.

## Приклад 4. async/await

```js
async function run() {
  console.log('1');

  await Promise.resolve();

  console.log('2');
}

console.log('3');

run();

console.log('4');
```

Результат:

```text

3

1

4

2

```

Пояснення:

1. Виконується `console.log('3')`.

2. Викликається `run()`, яка виводить `1`.

3. `await` призупиняє продовження функції.

4. Основний синхронний код виводить `4`.

5. Продовження async-функції виконується як мікрозадача та виводить `2`.

## Приклад 5. requestAnimationFrame та Promise

```js
console.log('start');

requestAnimationFrame(() => {
  console.log('animation frame');
});

Promise.resolve().then(() => {
  console.log('promise');
});

console.log('end');
```

Синхронна та мікрозадачна частини мають такий порядок:

```text

start

end

promise

```

Callback `requestAnimationFrame` виконується на етапі оновлення відображення браузера перед наступним малюванням.

Він не виконується синхронно і не є звичайним таймером. Його точний момент залежить від циклу рендерингу браузера.

# Лабораторна робота №5 — Server-authoritative Networking

## Мета роботи

Перенести обчислення руху кораблів на сервер, реалізувати детерміновану симуляцію з фіксованим кроком, клієнтське передбачення, підтвердження стану та компактний бінарний протокол.

## Архітектура

- `shared/simulation.js` — спільна детермінована функція руху корабля без залежності від DOM або Node.js.
- `shared/protocol.js` — бінарне кодування команд і знімків стану через `DataView` у little-endian.
- `server/src/websocket/server.js` — серверний цикл із частотою 30 тік/с. Наступний запуск планується від цільового часу через `setTimeout`, щоб не накопичувати дрейф `setInterval`.
- `client/src/main.js` — надсилання команд throttle/turn/fire із послідовним номером, локальне передбачення та повторне застосування непідтверджених команд після отримання snapshot.

## Протокол

Бінарна команда має 10 байтів: версія (1), тип (1), sequence (4), throttle (1), turn (2), fire (1). Кут повороту/керування передається як Int16. Snapshot містить версію, тип, номер серверного тіka, кількість гравців і записи стану гравців.

За замовчуванням використовується бінарний режим. Для порівняння JSON можна відкрити клієнт із параметром `?protocol=json`.

## Перевірка

1. Запустити сервер: `npm run dev:server`.
2. Запустити клієнт: `npm run dev`.
3. Відкрити гру у двох окремих вікнах браузера.
4. Ввести різні імена та приєднатися до однієї кімнати.
5. Перевірити рух обох кораблів і панель NETGRAPH.
6. Для JSON-режиму додати `?protocol=json` до адреси клієнта.

## Аналіз і обмеження поточної реалізації

Сервер є авторитетним для координат і швидкості кораблів: клієнт передає команди, а не готові координати. Клієнт зберігає чергу команд і після snapshot повторно застосовує команди, sequence яких ще не підтверджено сервером. Для точного вимірювання RTT потрібен окремий ping/pong із часовою міткою; у поточній панелі RTT позначено як недоступний. Значення трафіку та черги є локальними оцінками клієнта.

Бінарний протокол зменшує розмір повідомлень порівняно з JSON за рахунок фіксованих полів і числових типів. Сервер перевіряє команди, але для production-гри додатково потрібно винести постріли, кулі, зіткнення та шкоду в авторитетну серверну симуляцію. Також потрібні повноцінна інтерполяція віддалених гравців у минулому та згладжування корекцій протягом приблизно 100 мс.

## Lab 06 — TypeScript for protocol and simulation

The Lab 5 project is organized as three npm workspaces (`client`, `server`, and `shared`). The shared simulation and binary protocol have been migrated to TypeScript in the `@space-flight/shared` workspace.
`shared/types.ts` defines readonly vector/state contracts and branded `PlayerId`,
`RoomId`, `SimulationTick`, and `SequenceNumber` types. Snapshot entities use the
`kind: "ship"` discriminant. Exhaustive switches use `never` so adding a new entity
kind or client-message variant requires an explicit handler.

Runtime data is still untrusted: `server/src/websocket/validation.ts` uses Zod
schemas and `safeParse` for JSON WebSocket messages, while `server/src/config.ts`
validates environment configuration. The parser accepts `unknown`; malformed JSON
returns a validation result instead of escaping as an exception, is written to the
match log, and causes the socket to close. The browser WebSocket client also validates
incoming JSON server messages with Zod. The binary decoder checks packet length,
protocol version, field ranges, flags, and finite numeric values.

### TypeScript concepts used

- **Structural typing and inference:** interfaces describe the shape of simulation
  state and protocol messages; return types are inferred where the implementation
  makes them unambiguous.
- **`unknown` and narrowing:** JSON is parsed as untrusted input and is narrowed by
  Zod before application code can use it. No explicit `any` is used in the migrated
  TypeScript modules.
- **Discriminated unions and `never`:** message `type` and entity `kind` determine
  the available fields; exhaustive switches make missing cases a compile-time error.
- **Generics and `readonly`:** immutable state/vector contracts prevent accidental
  mutation at module boundaries; generic brands distinguish otherwise similar
  primitive identifiers.
- **Branded types:** player ID, room ID, simulation tick, and input sequence cannot
  be interchanged accidentally at compile time.
- **Strict compiler options:** `strict`, `noUncheckedIndexedAccess`,
  `exactOptionalPropertyTypes`, and `useUnknownInCatchVariables` are enabled.

### Errors and improvements found during migration

Reviewing the original binary decoder showed that it accepted any non-zero `fire`
byte as `true` and did not explicitly reject the reserved minimum values of the
signed throttle/turn fields. The TypeScript decoder now validates those ranges,
checks the protocol version and exact packet size, and rejects invalid flags and
non-finite snapshot values. This is runtime validation: TypeScript types are erased
when the program runs and cannot validate network bytes by themselves.

### Framework decision

The Canvas renderer and game loop remain framework-free. The assignment concerns
typing the protocol and deterministic simulation, not replacing the rendering
architecture. Introducing Svelte, Vue, or React only for the Lobby/HUD would add a
second UI architecture without improving the Canvas loop, so the existing DOM-based
Lobby and HUD are retained.

### Reflection

1. **Why use `unknown` instead of `any`?** `unknown` requires validation or type
   narrowing before a value can be used. `any` disables those checks and can let
   malformed network data flow into the simulation.
2. **Why are branded types useful?** `PlayerId`, `SimulationTick`, and
   `SequenceNumber` are all numbers at runtime, but they represent different
   concepts. Branding prevents accidental interchange in TypeScript code.
3. **Why is Zod still needed if the project uses TypeScript?** TypeScript checks
   source code before execution. It does not inspect incoming WebSocket JSON or
   binary packets at runtime, so Zod and explicit decoder checks validate external
   data.

After pulling the Lab 6 changes, run `npm install` once to install TypeScript, tsx, Zod, and refresh the npm lockfile. Run `npm run format` to format the migrated sources. Then run `npm run typecheck` to perform the strict TypeScript check and
`npm run test:determinism` to verify that the same fixed-step input sequence
produces the same final simulation state.


# Лабораторна робота №7 — V8, пам’ять і тести

## Автоматизоване тестування

Для тестування використовується Vitest. `tests/unit/shared.test.ts` перевіряє детерміновану симуляцію, двійковий протокол і runtime-схеми Zod. Property-based перевірки на fast-check охоплюють квантування input-пакетів, довжину пакетів, контрольовану відмову на пошкоджених даних, межі арени та валідацію повідомлень. Додаткові тести перевіряють `Vector2`, інтеграцію корабля, колізії, object pool, spatial hash, цикл кадру й життєвий цикл кімнат.

Команди:

```bash
npm run test                 # усі unit/property тести
npm run test:coverage        # тести з V8 coverage
npm run test:e2e             # Playwright: два ізольовані browser contexts
npm run test:load            # навантаження WebSocket 8/32/64/128 клієнтів
LOAD_DURATION_MS=30000 npm run test:load -- 8  # 8 клієнтів-ботів протягом 30 секунд
npm run ci                   # повний локальний CI
```

## E2E-сценарій

Playwright відкриває два незалежні Chromium contexts, під'єднує їх до кімнати `normal`, перевіряє доставку повідомлення чату та зміну координати першого гравця у snapshot після input-команди.

## Пам’ять і продуктивність

`Explosion` використовує пул частинок та оновлює координати без створення тимчасових векторів у кожному кадрі. Broad-phase зіткнень переведено на просторову хеш-сітку; narrow-phase залишає точну перевірку кіл. Потрібно перевіряти профіль до/після на однаковому сценарії, оскільки spatial hash має власну вартість побудови.

### V8: короткий теоретичний огляд

V8 спочатку розбирає JavaScript і компілює його у байткод для інтерпретатора Ignition. Гарячі ділянки можуть оптимізуватися TurboFan на основі профілю виконання та припущень про типи. Якщо припущення перестає бути правильним, можливі deoptimization і повернення до менш оптимізованого виконання. Hidden classes (Maps) описують форму об'єктів, а inline caches прискорюють повторний доступ до властивостей за стабільної форми. Тому властивості об'єктів бажано створювати в однаковому порядку й не змінювати їхню структуру в гарячих циклах.

Garbage Collector звільняє недосяжні об'єкти. Часті короткоживучі алокації збільшують роботу GC; object pool зменшує кількість повторних створень об'єктів, якщо об'єкти часто створюються й знищуються. Пул потрібно обмежувати й повертати об'єкти після використання, інакше він сам утримуватиме пам'ять.

### Web Worker

У поточній архітектурі стан симуляції містить взаємопов'язані змінювані Entity/Vector2 та використовується рендерером. Перенесення цього стану в Worker спричинило б копіювання або складну передачу буферів і синхронізацію кожного кадру. Без виміряного CPU-вузького місця та ізольованого компонента ботів це не дає обґрунтованої переваги, тому Worker не включений у головний цикл. Обґрунтування й умови перегляду рішення наведені у `docs/performance/LAB7-PROFILING.md`.
